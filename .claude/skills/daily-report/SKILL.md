# OffWay 개발 일지

그날 한 작업을 **한 장**으로 정리한다. 읽는 사람은 **팀 전체**다 — 디자인·기획도 보고, 개발도 본다.

**결과만 적지 않는다. 무엇이 문제였는지를 함께 적는다.** "푸시 알림이 잠금화면에 뜬다" 는 결과만 남기면,
12일 동안 안 보이고 있었다는 것도 발송은 성공으로 집계되고 있었다는 것도 사라진다. 그 사실이 그날 한 일의
값어치이자, 다음에 같은 함정을 피하는 근거다.

**그리고 보여준다.** 이 일지의 오른쪽 절반은 글이 아니라 그림이다. "열차 시간표가 비었다" 는 문장보다
`시간표 0편 → 6편` 두 칸이 빠르다. 개발이 아닌 사람이 읽는 자리라 더 그렇다.

## 핵심 원칙

- **항목 제목은 문제 서술이다.** `…었다 / …던 것` 으로 끝난다. "푸시 알림 배너 추가"(X) →
  **"붙여 둔 푸시가 12일 동안 아무에게도 안 보였다"**(O). 무엇을 했는지는 본문이 말한다.
- **지어내지 않는다.** 숫자는 **실측·집계된 것만** 올린다. 세어 보지 않은 수를 그럴듯하게 적지 않는다.
  근거는 머지된 PR·닫힌 이슈·커밋·그날의 실측이다. **그림도 마찬가지다** — 막대 길이가 실제 비율과
  다르면 그건 거짓말이다.
- **채울 것이 없으면 칸을 비우지 말고 항목 수를 줄인다.** 형식을 채우려고 없는 일을 만들지 않는다.
- **그릴 것이 없으면 안 그린다.** 비교할 전후가 없는 항목은 `.item-body` 에 `solo` 를 붙여 한 칸으로 편다.
  빈 상자를 두면 "뭔가 빠진 것" 처럼 보인다.
- **자정을 넘긴 작업은 시작일로 묶는다.** 밤 11시에 시작해 새벽 1시에 머지한 것은 그 전날 일이다. 자정으로
  끊으면 하루가 반 토막 나 보인다(실제로 8/30 리포트가 그렇게 2건짜리가 됐다).
- **리뷰에서 고친 것·고치다 만난 것도 그날의 일이다.** 화면 변화가 없어도 뒤쪽 항목으로 남긴다 — 그게
  하루의 절반인 날이 많다.
- **화면 변화가 없으면 그렇게 적는다.** "화면 변화는 없다" 로 시작하고 무엇이 나아졌는지 잇는다. 정당한
  답이지 회피가 아니다.

## 한 장의 구성

세로로 긴 한 장이다. 폭은 1000px 고정, 길이는 항목 수만큼 늘어난다.

| 자리 | 무엇 | 개수 |
|---|---|---|
| **머리** | `OFFWAY 개발 일지` + 제목(한 조각에 노란 하이라이트) + 리드 두세 문장 + **앱 목업** | — |
| **오늘의 숫자** | 그날을 숫자로. `전 → 후` 가 기본형 | 4 |
| **작업 항목** | 번호 + 문제 서술 제목 + 결 태그 + 설명 + **오른쪽 그림** | 7~10 |
| 바닥 | 날짜 · 머지된 작업 수 | — |

**앱 목업은 그날 바뀐 화면을 축소한 것이다.** 코스·지역처럼 화면이 바뀐 날에만 그린다. 바뀐 화면이
없으면 통째로 지우고 `.hero` 를 한 칸으로 편다 — 매일 같은 목업을 붙이면 그림이 정보를 잃는다.

## 오른쪽 그림 고르기

항목마다 하나를 고른다. **무엇을 보여줘야 하는가**로 정한다.

| 보여줄 것 | 쓸 것 | 예 |
|---|---|---|
| 무엇이 뜨고 안 뜨는가 | 상태 카드 `.tcard` | `열차 없음 / 시간표 0편` → `열차 / 시간표 6편` |
| 하루 일정이 어떻게 달라졌나 | 타임라인 `.tl` | 1일차가 비어 있던 것 → 네 칸이 찬 것 |
| 수치 하나가 줄거나 늘었나 | 막대 `.bars` | `18초 → 6초`, `26.5㎞ → 24.0㎞` |
| 후보 중 무엇이 뽑히나 | 칩 `.chips` | 수서 5.80(취소선) · **왕십리 6.02**(선택) |
| 여러 수치를 나란히 | 키-값 `.kv` | 스왑 0 · 캐시 8.9GB · 여유 387MB |
| 그릴 것이 없다 | `solo` | 규칙·판단만 바뀐 항목 |

**전/후 두 칸(`.cmp`)이 기본이고, 한 장으로 충분하면 `.panel` 을 쓴다.** 막대는 보통 한 장 안에
전·후 두 줄을 넣는 편이 읽기 쉽다.

`.tag` 는 그 항목의 결을 한 단어로: `데이터` · `추천 규칙` · `콘텐츠` · `속도` · `내부` · `신규` · `인프라`.

## 절차

### 1. 사실을 긁는다 — 추측하지 않는다

작업 시작일(KST)을 정하고, **자정을 넘겼으면 그 전날로 묶는다**.

```bash
# 작업 세션 구간으로 본다 (자정 넘긴 머지를 놓치지 않게)
gh pr list --state merged --search "merged:<시작>..<끝>" --json number,title,labels
gh issue list --state closed --search "closed:>=<시작>" --json number,title
git log --since="<시작>" --pretty="%h %cI %s" origin/dev
```

숫자를 쓸 거면 그 자리에서 센다 — 테스트 수, 처리한 리뷰 지적 수, 실측값. **대화에서 이미 잰 값이 있으면
그것을 1순위로 쓴다.**

### 2. 항목으로 재구성한다

항목 하나가 보통 PR 하나다. 쓰기 전에 스스로 묻는다:

- *무엇이 문제였나* → 제목
- *왜 그게 문제였나 / 얼마나였나* → 설명
- ***이걸 한 장면으로 보이면 무엇인가*** → 오른쪽 그림

**번호는 그날의 무게 순이다.** 사용자가 겪던 문제가 앞, 내부 개선이 뒤다. 리뷰 지적·고치다 만난 것은
뒤쪽에 모으되 같은 형식으로 쓴다 — 별도 섹션으로 격을 낮추지 않는다.

### 3. 렌더하고 캡처한다

`assets/report-template.html` 을 `docs/specs/progress-report-<MMDD>.html` 로 복제해 내용만 갈아끼운다.

```bash
CHROME="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
"$CHROME" --headless --disable-gpu --hide-scrollbars \
  --screenshot="$(pwd)/docs/specs/progress-report-<MMDD>.png" \
  --window-size=1100,<내용높이> --force-device-scale-factor=2 \
  "file://$(pwd)/docs/specs/progress-report-<MMDD>.html"
```

**폭은 1100 이다.** 본문이 1000px + 좌우 여백이라 그보다 넓게 잡으면 빈 여백만 늘어난다.
**높이는 내용에 맞춘다** — 한 번 크게 찍어 보고 아래 여백만큼 줄여 다시 찍는다. 항목 열 개면 대략 3200~3800.

**워크트리에서 작업 중이면 메인 체크아웃에도 복사한다.** 사용자가 그쪽 폴더를 열기 때문에, 안 하면 낡은
파일을 보게 된다(실제로 그랬다).

```bash
cp docs/specs/progress-report-<MMDD>.png <메인체크아웃>/docs/specs/
open -R <메인체크아웃>/docs/specs/progress-report-<MMDD>.png
```

**리포트 파일은 커밋하지 않는다** — 기능 PR 에 섞이면 안 되는 산출물이다(`/commit` 의 제외 대상).

## 톤

담백하고 자신감 있게. 과장·이모지 금지. **"됐다/실제로 돈다"는 근거 있을 때만.**

강조는 셋뿐이다 — 제목의 **노란 하이라이트 한 곳**, 본문의 `<b>`(사실), `.g`(나아진 것). 문장마다 뿌리지
않는다. 다 강조하면 아무것도 강조되지 않는다.

숫자에는 단위를, 비교에는 전후를 붙인다(`16 → 25곳`, `12일`, `5곳 / 89`).
