# 백오피스 썸네일 업로드 열기 (#377)

백오피스에서 이미지를 **골라서** 올릴 수 있게 만드는 절차다. **코드 배포만으로는 안 열린다** — 버킷과
IAM 자격증명은 코드가 만들 수 없다.

| # | 무엇 | 담당 | 없으면 |
|---|---|---|---|
| 1 | ~~공개 읽기 정책~~ | — | **이미 되어 있다** (아래 참고) |
| 2 | 업로드 전용 IAM 사용자·키 발급 | **사람** | 업로드 주소 발급이 `502 CURATION-009` |
| 3 | 버킷 CORS 허용 | **사람** | 발급은 되는데 브라우저의 `PUT` 이 CORS 로 막힌다 |
| 4 | GitHub 시크릿 3개 등록 | **사람** | 위와 같음 |

**열기 전에도 배포는 나갈 수 있다.** 자격증명이 없으면 어댑터가 비활성으로 뜨고 발급만 실패한다 —
부팅과 나머지 기능은 그대로고, 어드민은 지금까지처럼 **주소 붙여넣기** 탭으로 등록한다.

---

## 1. 버킷 — 이미 있는 것을 쓴다

**`offway-images-996918499382` (도쿄 `ap-northeast-1`)** 를 그대로 쓴다. 새로 만들지 않는다.

| 항목 | 값 | 왜 괜찮나 |
|---|---|---|
| 이름 | `offway-images-996918499382` | 점(`.`)이 없어 기본 공개 주소가 TLS 에서 막히지 않는다(아래 참고) |
| 리전 | `ap-northeast-1` | EC2·보안그룹·배포 워크플로우가 전부 도쿄다 |
| 퍼블릭 액세스 차단 | **해제되어 있어야 한다** | 객체를 공개로 읽어야 앱이 썸네일을 그린다 |

**남의 용도와 섞이지 않는다.** 우리가 쓰는 것은 `curation/` 아래뿐이고, 아래 정책과 IAM 권한도 그
접두사로 좁혀 둔다. 이 버킷에 다른 것이 들어 있어도 서로 건드리지 않는다.

> ### ⚠️ 기존 정책·CORS 를 덮어쓰지 않는다
>
> 버킷 정책도 CORS 도 **문서 하나**다. 콘솔에서 아래 JSON 을 그대로 붙여넣으면 지금 걸려 있는 것을
> **통째로 대체**한다 — 이 버킷을 쓰던 다른 것이 조용히 깨진다.
>
> 이미 뭔가 걸려 있으면 **`Statement` 배열에 항목을 더하는** 방식으로 합쳐야 한다.

> **버킷 이름에 점을 넣지 않는다.** 공개 주소를 따로 주지 않으면 서버가
> `https://{버킷}.s3.{리전}.amazonaws.com` 형식으로 만드는데, 이름에 점이 있으면 그 호스트명이
> `*.s3.{리전}.amazonaws.com` 와일드카드 인증서와 맞지 않아 **브라우저가 TLS 에서 막는다.** 업로드는
> 성공하고 저장까지 끝난 뒤에야 이미지가 안 열리는 것으로 드러난다. 점이 필요하면 `S3_PUBLIC_BASE_URL`
> 을 반드시 채운다 — 서버가 부팅 로그에 그 경고를 남긴다.

### 정책은 손대지 않는다 — 이미 걸려 있다 (확인 2026-09-01)

```json
{
  "Sid": "PublicReadOnly",
  "Effect": "Allow",
  "Principal": "*",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::offway-images-996918499382/*"
}
```

**버킷 전체가 공개 읽기**라 `curation/*` 는 이미 포함된다. 더할 것이 없다.

**대신 알고 있어야 하는 것**: 이 버킷에 넣는 것은 무엇이든 공개다. 썸네일은 어차피 공개할 값이라
문제없지만, 나중에 여기에 공개하면 안 되는 것을 넣으면 그대로 열린다.

**쓰기는 presigned 로만 들어온다.** 정책 어디에도 `s3:PutObject` 가 없고, 앞으로도 더하지 않는다.

## 2. IAM

**업로드 전용 사용자를 새로 만든다(`offway-uploader`).** 배포용 `offway-deploy` 를 재사용하지 않는다.

편의 문제가 아니라 **위험 범위** 문제다. `offway-deploy` 는 EC2 보안그룹을 여는 권한이 있고(배포가
러너 IP 를 22번에 추가한다), 지금 그 키는 **GitHub Actions 안에만** 있다. 그런데 `S3_ACCESS_KEY` 로
같은 키를 쓰면 그것이 EC2 의 `~/offway/env.prod` 로 내려가 **컨테이너에 상주**한다 — 서버가 털렸을 때
보안그룹을 여는 자격까지 함께 넘어간다. 지금 그 키가 서버에 없다는 것이 방어선인데 스스로 무너뜨리는
셈이다.

키를 돌릴 때 배포와 업로드가 함께 멈추는 것도 재사용의 대가다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::offway-images-996918499382/curation/*"
    }
  ]
}
```

**`s3:PutObject` 하나면 된다.** 서버는 올리지도, 지우지도, 목록을 보지도 않는다 — 서명만 만든다.
`s3:DeleteObject` 를 주면 그 권한이 서명에도 실릴 수 있는 자리가 생기므로 주지 않는다.

읽기는 버킷 전체가 공개인데 **쓰기만 `curation/*` 으로 좁히는 것이 의도한 비대칭**이다. 읽기 범위는
이미 정해져 있던 것이고, 쓰기는 우리가 정할 수 있으니 좁게 잡는다 — 키가 새도 다른 접두사의 파일을
덮어쓰지 못한다.

액세스 키를 발급해 다음 단계에 쓴다.

## 3. CORS

브라우저가 **우리 서버가 아니라 S3 로 직접** `PUT` 하므로, 버킷이 우리 도메인을 허용해야 한다. 이걸
빼면 발급까지는 성공하고 업로드만 조용히 막힌다 — 콘솔에만 CORS 오류가 뜬다.

**이미 규칙이 있다(확인 2026-09-01).** `PUT` 도 허용돼 있고 `AllowedHeaders` 가 `*` 라 서명이 요구하는
`Content-Type` 도 통과한다. **빠진 것은 origin 하나** — 백오피스가 뜨는 `https://api.offway.cloud` 다.

**규칙을 갈아치우지 말고 `AllowedOrigins` 배열에만 더한다.**

```json
[
    {
        "AllowedHeaders": ["*"],
        "AllowedMethods": ["PUT", "GET", "HEAD"],
        "AllowedOrigins": [
            "https://offway.cloud",
            "https://www.offway.cloud",
            "https://api.offway.cloud",
            "http://localhost:5173",
            "http://localhost:3000",
            "http://localhost:8080"
        ],
        "ExposeHeaders": ["ETag"],
        "MaxAgeSeconds": 3000
    }
]
```

`http://localhost:8080` 은 로컬에서 백오피스를 띄워 업로드를 시험할 때만 필요하다. 이 버킷은 이미
`5173`·`3000` 을 받고 있어 관례가 서 있지만, 원치 않으면 그 줄만 빼면 된다.

## 4. 환경변수

**워크플로우 쪽은 이미 되어 있다** — `deploy.yml` 이 아래 이름들을 컨테이너 환경변수로 넘긴다.
GitHub 시크릿(레포 Settings > Secrets and variables > Actions)에 값만 넣으면 다음 배포부터 붙는다.
등록하지 않은 이름은 빈 값으로 나가고, 그때는 업로드가 비활성일 뿐 부팅은 정상이다.

| 이름 | 값 | 비우면 |
|---|---|---|
| `S3_BUCKET` | `offway-images-996918499382` | 업로드 비활성 |
| `S3_REGION` | `ap-northeast-1` | 기본값이 이미 도쿄다. **시크릿으로 받지 않는다** — 바꿀 일이 생기면 코드 기본값을 고친다 |
| `S3_ACCESS_KEY` | 2번의 액세스 키 | 업로드 비활성 |
| `S3_SECRET_KEY` | 2번의 시크릿 | 업로드 비활성 |
| `S3_PUBLIC_BASE_URL` | CloudFront 를 앞에 둘 때만 | 버킷 기본 주소를 쓴다 |

넷(`BUCKET`·`REGION`·`ACCESS_KEY`·`SECRET_KEY`) 중 **하나라도 비면** 업로드가 비활성이다. 반쯤 채워
두면 서명은 만들어지는데 S3 가 거절해, 어드민이 올리기를 누른 뒤에야 실패를 알게 된다. 그래서 서버가
발급 단계에서 미리 끊는다.

## 확인

1. 백오피스에서 링크를 하나 열고 **썸네일 > 업로드** 탭에서 이미지를 고른다
2. "올렸습니다" 가 뜨면 **저장**을 누른다 — 올리기만 하고 저장하지 않으면 아무 데도 안 걸린다
3. 목록의 썸네일과 앱 카드에 그 이미지가 보이면 끝

실패하면 문구가 사유를 그대로 말한다.

| 문구 | 무엇이 빠졌나 |
|---|---|
| 이미지 저장소를 사용할 수 없습니다 | 4번 환경변수 (또는 넷 중 하나가 빔) |
| `S3 403` | 2번 IAM 정책의 Resource 가 키와 안 맞음 |
| 콘솔에 CORS 오류 | 3번 |
| 업로드는 되는데 이미지가 안 열림 | 버킷 이름에 점이 있고 `S3_PUBLIC_BASE_URL` 이 빔 (1번 참고) |

## 남는 것 — 버려지는 오브젝트

주소만 받고 저장하지 않거나, 올린 뒤 폼을 닫으면 **아무 데서도 참조하지 않는 오브젝트**가 남는다.
지금은 그대로 둔다 — 어드민 몇 명이 쓰는 화면이라 쌓이는 양이 적고, 지우려면 "저장 안 된 오브젝트" 를
판정하는 배치가 따로 필요한데 그 값이 아직 비용보다 크지 않다.

양이 눈에 띄게 늘면 버킷 수명 주기 규칙(예: `curation/` 아래 30일 이상 된 것 중 참조 없는 것)을 그때
정한다.
