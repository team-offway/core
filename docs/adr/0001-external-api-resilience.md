# ADR 0001 — 외부 API resilience 전략

- 상태: 채택(2026-07-28)
- 관련: `common/cache/ExternalDataCache`, `trip/service/HomeCacheWarmer`, `RegionRankingService`·`RegionContentProvider`·`AirQualityService`

## 맥락

OffWay 는 데이터 주도 서비스라 화면 하나를 그리려면 **여러 외부 공공 API** 를 모은다.

| 외부 API | 소유 도메인 | 성격 |
|---|---|---|
| 관광빅데이터(생활인구) | trip | 랭킹 가중치. 시도당 페이지네이션, **수 초**, 월간·15일 지연 |
| TourAPI(지역 콘텐츠·POI) | trip | 카드 이미지·볼거리. 지역당 **수 초**, 간헐 타임아웃 |
| 에어코리아(미세먼지) | weather | 부가 정보. 시도당 **2~5초**, 시간당 갱신 |
| 기상청(단기예보) | weather | 부가 정보. 좌표·날짜, 예보 범위 3일 |
| TMAP(경로·이동시간) | transport | 코스 이동시간. **사용자 입력(출발지·날짜) 의존** |
| 특일정보(공휴일) | leave | 연차 계산. 연 단위, 안정적 |

공통 문제는 셋이다.

1. **지연** — 각 호출이 초 단위라, 요청 경로에서 여러 개를 동기로 부르면 워터폴로 수십 초가 된다.
2. **쿼터·불안정** — 공공 API 는 일일 호출 한도가 있고 간헐적으로 실패·타임아웃한다. `지역 수 × 사용자 수` 만큼 외부를 때리면 금방 막힌다.
3. **키 보안** — 서비스키를 클라이언트에 노출할 수 없다.

## 결정

**클라이언트가 외부를 직접 부르지 않는다.** 서버가 외부 API 를 모아 캐싱하고, 화면 단위로 한 번에 내려준다(외부 API 집계 레이어 + 서버사이드 캐싱). 그리고 외부 의존을 다루는 **공통 규율**을 하나의 프리미티브(`ExternalDataCache`)에 담아 모든 외부 클라이언트가 같은 방식으로 견고해지게 한다.

> 용어: 이 구조는 "BFF"(클라이언트 종류별 전용 백엔드)가 아니다. 단일 백엔드가 외부를 집계·캐싱하는 것이다.

### 담긴 규율

- **키별 TTL 캐시** — 값마다 신선도 기간을 데이터 특성에서 도출해 정한다. 예: 생활인구는 "월간·15일 지연이라 6시간이 신선도 손해 없음", 미세먼지는 "시간당 발표라 1시간".
- **degrade vs 502 결정** — "멀쩡한 클라이언트가 정상 요청으로 여기 닿나?"가 아니라 "이 데이터가 화면의 본질인가, 부가인가"로 가른다.
  - **부가/가중치**(랭킹·콘텐츠·미세먼지·날씨) → 실패해도 예외를 올리지 않고 degrade(빈 값·폴백 랭킹). 화면은 200 으로 뜬다.
  - **본질**(장소 상세 `GET /pois/{id}` 의 콘텐츠) → degrade 할 게 없으므로 502 유지.
- **single-flight + double-check** — 캐시 만료 순간 같은 키에 요청이 몰려도 한 스레드만 재조회하고 나머지는 stale 값을 즉시 받는다. 게이트 획득 직후 캐시를 재확인해 직렬 중복 호출도 막는다. 잠금은 외부 I/O 동안 잡지 않는다.
- **stale-while-error** — 재조회 실패 시 마지막 성공값을 계속 내려준다.
- **negative caching** — 실패·빈 값은 짧은 TTL(5분)로 눌러둬, 외부가 죽어 있을 때 매 요청이 초 단위로 재시도하는 것을 막는다.
- **프리워밍**(`HomeCacheWarmer`) — 89개 고정 지역 캐시를 부팅 후·주기적으로 **요청 경로 밖**에서 채운다. 워밍 주기(5h)는 TTL(6h)보다 짧아 항상 fresh. 실패는 단계·지역별로 격리해 워밍이 서비스를 죽이지 않는다.
- **키 없이도 부팅**(로컬 실행성) — 어댑터는 키가 없으면 외부 호출 없이 빈 결과. 이 캐시·degrade 규율이 그 위에서 동작한다.

## 적용 범위

| | 관광빅데이터 | TourAPI 콘텐츠 | 에어코리아 | TMAP(코스) | 특일정보 |
|---|---|---|---|---|---|
| TTL 캐시 | ✅ 6h | ✅ 6h | ✅ 1h | ➖ | (연 단위) |
| single-flight | ✅ | ✅ | ✅ | ➖ | ➖ |
| stale-while-error | ✅ | ✅ | ✅ | ➖ | ➖ |
| degrade | ✅ 폴백 랭킹 | ✅ 빈 콘텐츠 | ✅ null | 직선거리 폴백 | — |
| 프리워밍 | ✅ | ✅ | ✅ | ❌(불가) | ➖ |

## 캐싱할 수 없는 것 — 코스 생성

홈·추천은 89개 **고정** 지역이라 미리 데울 수 있어 ms 응답이 된다. 그러나 **코스 생성은 프리워밍이 불가능**하다. TMAP 이동시간이 사용자 입력(출발지·여행 날짜·이동수단)에 따라 매번 달라져, 미리 계산해둘 대상이 없기 때문이다. "미리 데울 수 있는 것과, 입력에 따라 달라져 그럴 수 없는 것"을 나누는 것이 이 전략의 경계다.

## 트레이드오프 — 단일 인스턴스 전제

캐시는 각 서비스의 **JVM 인메모리**(`ExternalDataCache`)다. 인스턴스를 늘리면 히트율이 나뉘고 워밍·single-flight 가 인스턴스별로 따로 돌아 외부 호출·쿼터 소모가 인스턴스 수만큼 는다. 공모전 규모(단일 인스턴스)에선 로컬 캐시가 더 빠르고 단순해 **의식적으로** 택했다. `build.gradle.kts` 에 Redis 의존성이 이미 있어, 스케일아웃하면 동일 인터페이스로 공유 캐시(Redis)로 옮기고 워밍은 리더 1대만 돌린다.

## 결과

- 홈: 간헐 502 → **항상 200**, 6~21초 → **수 ms**(워밍 후).
- 외부가 전부 죽어도 화면은 degrade 된 형태로 뜬다.
- 새 외부 소스를 붙일 때 `ExternalDataCache` 위에 올리면 같은 견고함을 자동으로 얻는다(교통 클라이언트가 그 예).
